# AI作業環境・工程接続原則

## 1. 目的

本Sourceは、フェミニンウェルネス生涯教育事業のAI組織が、Chat、Work、Codex、VS Code、Repository、Git、GitHubおよび外部AIを、どの責任段階で使用し、どのように接続するかを定義する。

目的は、環境ごとに同じ責任を重複配置することではない。

> AI組織上の責任を維持したまま、判断、制作、監査、修正、Repository反映および変更管理を、適切な環境へ接続する。

人間がAI間・環境間の単純な転記、保存、運搬、状態同期および定型工程の起動だけを担う構造を標準運用としない。

---

## 2. 適用範囲

本Sourceは、次の環境および接続を対象とする。

- Chat
- Work
- Codex
- VS Code
- Repository
- Git
- GitHub
- Claude等の外部AI
- OneDrive上の `AI/00_Inbox` および `AI/04_Personal_Archive`
- 上記環境間の作業指示、成果物、監査結果および状態情報の受け渡し

OneDrive上のInboxおよびPersonal Archiveは、Repository外の管理対象領域である。受領、配属、検証、ClosedならびにOriginal、ProcessedおよびDerivedの責任境界は、`04_AI_Work_Environment/INBOX_AND_PERSONAL_ARCHIVE.md` を正とする。

これらの領域をRepositoryまたは正式Source置場として扱わない。

本Sourceは、個別サービス固有の制作フロー、公開フロー、アカウント操作、料金支払い、外部送信その他の詳細手順を定義しない。

note、SNS、教材制作その他の個別E2Eフローは、それぞれの責任Sourceが必要になった時点で定義する。

本Sourceは、作業環境と工程接続を扱う独立した横断運用責任単位の正式Sourceである。

Repository上の具体的な配置、ディレクトリ構造、CHANGELOGおよび変更記録は、本Sourceでは定義せず、`REPOSITORY_RULES.md` を正とする。

## 3. 上位・関連Sourceとの責任分離

本Sourceは、各作業環境の役割と工程接続を担う横断運用Sourceである。

次の既存Sourceの責任を移管、代替または重複定義しない。

### AI組織構造・担当権限

`AI_ORGANIZATION.md` を正とする。

本Sourceは、新しいAIの役割、部署、専門責任、承認者または組織階層を定義しない。

### Human-in-the-loop

人間とAIの承認境界、自動進行条件、停止条件、再承認条件、エスカレーション、自己復旧、個別指示および完了判断は、`03_Human_in_the_Loop/HUMAN_IN_THE_LOOP.md` を正とする。

本Sourceは、人間承認の要否や停止条件を新しく決定せず、既存の承認境界に従って作業環境とChatを接続する。

### Repository・Git・CHANGELOG

Repository構造、正式配置、Archive、GitおよびCHANGELOGの具体運用は、`REPOSITORY_RULES.md` を正とする。

案件ごとのSource選択、Source QA、Production、Repository IntegrationおよびGitまでの共通SOPは、`AI_PRODUCTION_PIPELINE.md` を正とする。Repository全体へ影響する正式Source変更の横断確認は、`REPOSITORY_CROSS_AUDIT_STANDARD.md` を正とする。

本Sourceは、これらのSOP・監査基準が要求する作業環境の接続を担うが、Source選択基準、監査基準、正式承認またはRepository配置の具体規則を重複定義しない。

### Brand

Brand固有の思想、理念、表現、ガバナンスおよびAI共創思想は、Brand各正式Sourceを正とする。

### Education

教育内容、教育設計、教材制作、教育品質、Version、Statusおよび最終承認は、Education各正式Sourceを正とする。

### Voice

Voice OSの適用対象、本人固有のVoiceおよびコミュニケーション判断は、`02_Voice_OS/VOICE_OS.md` と、その適用関係を定めるRepository・専門Sourceを正とする。

## 4. 基本原則

### 4.1 環境は責任段階に応じて選ぶ

Chat、Work、Codex等を、すべての仕事で機械的に順番に通過させない。

作業目的、判断の有無、制作規模、Repositoryとの接続および必要な品質保証に応じて、必要な環境だけを使用する。

### 4.2 正式Sourceを優先する

Chat、Work、外部AIその他の環境に存在する文章は、それだけで正式Sourceにならない。

現在有効な判断では、Repositoryに配置された現行正式Sourceを優先する。

ただし、正式Sourceを更新する作業中は、承認済みの変更内容とローカル作業ツリーの最新差分を無視して、古いcommitまたはremote状態へ戻らない。

### 4.3 品質保証工程を削らない

制作、内部監査、修正、影響確認、再確認、必要な独立監査および正式承認は、責任Sourceが要求する範囲で維持する。

削減対象は、各工程を一つずつ起動・中継するためだけの不要な人間操作である。

### 4.4 人間判断のUIはChatへ集約する

人間が理解、選択、承認、方針決定または新規判断を行う必要がある場合は、原則としてChatへ戻す。

Work、Codexまたは外部AIが、それぞれ別の場所で人間へ判断を要求する構造を標準運用としない。

人間判断の要否、停止条件および再承認条件は `HUMAN_IN_THE_LOOP.md` を正とする。

### 4.5 環境名とAI組織上の役割を混同しない

Chat、Work、Codex等は作業環境または実行形態であり、それ自体が新しいAI組織上の役職や責任主体になるとは限らない。

誰が制作、監査、修正または承認を担うかは、`AI_ORGANIZATION.md` と専門Sourceを正とする。

## 5. Chat

Chatは、人間とAIが考え、理解し、方針・意味・採否・承認を決める意思決定レイヤーである。

主な用途は次のとおりとする。

- 壁打ち
- 相談
- 企画
- 目的と完了条件の確認
- 方針決定
- 意味の確認
- 複数の合理案からの選択
- AIが一意に確定できない事項の判断
- 外部監査指摘の理解と、人間判断領域に関する採否判断
- 人間承認
- AIワークフローの起動

Chat上の会話履歴を、そのまま後工程の完全な作業指示として扱わない。

後工程へ渡す際は、AIが確定事項、参照Source、対象、制約、未採用案、停止条件および完了条件を整理する。

Chatは正式Sourceの保存場所ではない。

Chatで確定した判断を恒久的に使用する必要がある場合は、責任を持つ正式Sourceまたは承認記録へ反映する。

---

## 6. Work

Workは、確定した目的・方針・仕様をもとに、成果物を制作・監査・修正し、完成状態まで育てる継続作業空間である。

主な用途は次のとおりとする。

- 長文成果物の制作
- 設計書の作成
- 複数回の修正
- 内部監査
- 監査指摘に基づく修正
- 再監査
- 複数Sourceとの整合確認
- 制作途中コンテキストの保持
- Repository反映前の制作中最新稿の保持

Workは正式SourceまたはRepository上の正本ではない。

Repositoryへ反映する前に独立した制作・監査作業空間が必要な案件では、制作中成果物の現在稿を保持するために使用できる。

同一成果物について複数稿が存在する場合は、環境間受け渡し情報において、少なくとも次を明示する。

- 対象成果物
- 対象稿
- 現在状態
- 次工程へ渡す稿
- 未解決事項

更新日時、名称または会話上の位置だけから、現在の作業対象を推測しない。

既存基準から一意に判断できる制作、内部監査、修正および再確認は、Work内で連続実行できる。

新しい思想、仕様、責任、重要な採否または人間承認が必要になった場合はChatへ戻す。

Workをすべての案件の必須経由点にはしない。

---

## 7. Codex

Codexは、Repositoryを直接参照し、正式Sourceとの整合を保ちながら、実装・反映・検証を行う実行環境である。

主な用途は次のとおりとする。

- Repository READ
- 現行正式Sourceと関連ファイルの探索
- 現在の作業ツリーと差分の確認
- 保存先と責任領域の確認
- 新規ファイル作成
- 既存Source修正
- 承認済み目的に必要な波及修正
- CHANGELOG要否の判定と更新
- 構造、配置、参照、命名および形式の確認
- 内部監査
- 既存基準内の修正
- 修正後再確認
- `git diff`
- `git diff --check`
- 必要なGit操作

Codexを単なる保存係に限定しない。

Repositoryと正式Sourceを直接参照することに意味がある作業では、Codex自身が制作・修正・内部監査を担うことができる。

ただし、Codexによる内部監査・自己確認は、責任Sourceが要求する独立監査、制作後レビュー、最終承認または人間承認を代替しない。

Codexが自ら制作・修正したことと、その成果物を正式承認できることを同一視しない。

Codexは次を独自に行わない。

- Brand思想の新規決定
- Education方針または教育内容の新規決定
- 人間承認の代行
- 既存Sourceから一意に導けない重要仕様の確定
- 未承認の責任配置変更
- 未定義の対外公開、送信または支払い
- 制作主体としての自己承認

これらが必要になった場合は、`AI_ORGANIZATION.md`、専門Sourceおよび `HUMAN_IN_THE_LOOP.md` に従い、適切な責任主体またはChatへ接続する。

## 8. WorkとCodexの環境選択

WorkとCodexは必須の直列工程ではない。

標準的な経路には、次を含む。

### Chat → Codex

次の場合に使用できる。

- 目的、仕様、変更範囲および完了条件が確定している
- Repository上で直接制作・修正する方が合理的
- 独立した長期制作空間を必要としない
- 既存Sourceと作業ツリーを直接確認する必要がある

### Chat → Work → Codex

次の場合に使用できる。

- 長文設計や複数回の壁打ち後修正が必要
- Repositoryへ反映する前に独立した制作・監査空間が必要
- 完成稿を確定してから正式配置する方が安全
- 制作途中の試行をRepositoryから分離する必要がある

### Work → Chat → Work → Codex

Work中に新しい人間判断が必要になった場合に使用する。

Chatで判断確定後、Workが制作・監査を再開し、完成稿をCodexへ渡す。

### Codex → Chat → Codex

Repository調査または実装中に、人間判断が必要な未定義事項が判明した場合に使用する。

環境選択の中心基準は次のとおりとする。

> Repositoryへ反映する前に、独立した制作・監査作業空間が必要か。

不要な環境を形式的に経由しない。

## 9. VS Code

VS Codeは、人間がRepositoryを閲覧、確認し、必要に応じて編集する操作画面である。

VS Code自体を正式Source、承認者、履歴管理システムまたは作業状態の正本として扱わない。

VS Codeで表示されるファイルの責任と状態は、Repository、Gitおよび各専門Sourceに従う。

Codexと人間が同じファイルを同時に編集しない。

人間がVS Codeで編集を開始した場合、Codexへ対象ファイルと編集範囲を共有する。Codexは作業開始時およびWRITE直前に現在の差分を確認し、他者の未保存・未確認変更を推測で上書きしない。

競合または編集主体を確定できない場合は、変更を統合せず、`HUMAN_IN_THE_LOOP.md` に従って停止・接続する。

## 10. Repository・ローカル作業ツリー・Git・GitHub

### 10.1 Repository

Repositoryは、正式Source、成果物、承認記録、変更履歴ファイルおよび必要な過去資産を、定義された責任構造に従って保持する場所である。

Repositoryへ存在することだけで、成果物がApprovedになるわけではない。

正式使用可否は、適用される専門Sourceと承認工程を正とする。

### 10.2 ローカル作業ツリー

ローカル作業ツリーは、未commit変更を含む現在編集中の最新状態を保持する。

未commitであることだけを理由に、変更内容を無効または存在しないものとして扱わない。

一方、未commit変更を、品質保証と承認を通過した確定履歴として扱わない。

AIは作業開始時に現在の差分を確認し、既存の未commit変更を保持する。

### 10.3 Git commit

Git commitは、確認済みの変更単位について変更履歴を確定する。

commitは、Brand、Educationその他の専門領域における人間承認や正式承認を代替しない。

commitの具体運用とメッセージ規約は `REPOSITORY_RULES.md` を正とする。

### 10.4 GitHub

GitHubは、remoteへ反映済みのRepository状態を保持する共有・復旧先である。

ローカル作業ツリーに未pushの変更がある場合、GitHubは現在作業中の最新状態ではない。

pushは、確認済みcommitをremoteへ反映する工程であり、専門領域の承認を新たに発生させる工程ではない。

### 10.5 Git反映周辺の部分工程

本節はE2E全体を定義するものではなく、必要な制作、専門QA、監査、正式承認、CHANGELOG要否判定および必要な履歴更新を前段で満たした後の、Git反映周辺の部分工程を示す。

代表的な部分工程は次のとおりとする。

構造・配置・参照・命名の確認\
→ `git diff`\
→ `git diff --check`\
→ 必要な影響範囲確認\
→ commit\
→ push\
→ remote反映確認\
→ 作業ツリー確認

commit・pushを実施できる条件は、`HUMAN_IN_THE_LOOP.md` と `REPOSITORY_RULES.md` を正とする。

本節を根拠として、未完了の専門承認、監査またはCHANGELOG処理を省略しない。

## 11. branch・pull request

現在の実運用ではmainを直接使用しており、branchおよびpull requestは正式導入されていない。

これは現状の参照情報であり、本SourceがGit運用規範としてmain直接運用を新しく確定するものではない。

branch、pull request、導入条件、命名、レビュー、mergeその他のGit運用規範は、本Sourceでは定義しない。

Git運用規範は `REPOSITORY_RULES.md` を正とする。

将来、branchまたはpull requestを正式導入する場合は、Repository運用上の変更として適切な判断とSource更新を経る。

## 12. 外部AI

Claude等の異種AIは、原則として助言的監査役として使用する。

外部AI監査を、すべての成果物へ一律に適用しない。

外部AI監査は、異なるモデルによる独立視点、抜け・矛盾の検出、構造上の違和感または別解釈の確認によって得られる便益が、追加工程、情報提供、確認および再監査の負荷を上回る場合に使用する。

特に次の場合は、外部AI監査を追加する必要性を確認する。

- 新しい正式Sourceとして採用する前
- 複数Sourceを対象とする横断監査
- 複数案件または後続工程で高い再利用性を持つ成果物
- 公開、顧客、受講者、事業判断その他への対外影響が大きい成果物

これらに該当することだけで、外部AI監査が自動的に必須になるわけではない。対象の重要性、既存監査の独立性、誤りの影響、機密性および追加負荷を踏まえて必要性を判断する。

個別成果物または個別業務フローについて、外部AI監査を必須、任意または不要のどれとするかは、その成果物・業務フローを管理する責任Sourceが定義する。

本Sourceでは、note、SNSその他の個別媒体名を根拠とする固定的な監査要否を定義しない。

外部AI監査を追加した場合も、既存の内部QA、Human-in-the-loop、人間判断、専門監査または正式承認工程を代替しない。

外部AIへ提供する情報は、監査目的に必要な範囲へ限定する。

原則として次を提供する。

- 監査対象
- 監査目的
- 適用される正式Source
- 必要な上位Source
- 変更禁止事項
- 監査観点
- 期待する指摘形式

Repository全体を機械的に渡さない。

監査対象と判断基準を理解するためにRepository全体が必要な場合のみ、権限、機密性、外部共有制限および提供手段を確認したうえで扱う。

原則として次を渡さない。

- 監査目的と無関係なSource
- 認証情報
- APIキー
- 個人情報
- 未承認の機密情報
- 外部共有が許可されていない資料
- Repository操作権限
- 正式Sourceへの直接WRITE権限

監査結果は、元の制作・修正責任側へ戻す。

- Workで作成した成果物の監査結果は、原則としてWork側へ戻す
- Codexで作業した成果物の監査結果は、原則としてCodex側へ戻す
- 人間判断が必要な指摘は、元担当側が争点、根拠、影響および推奨案を整理してChatへ戻す

制作・修正担当の裁量を超える指摘は、使用環境だけで差し戻し先を決めず、`AI_ORGANIZATION.md` および専門Sourceが定める上位責任AI、教育設計側その他の責任主体へ差し戻す。

環境上の返却先と、AI組織上の責任主体を混同しない。

外部AIの出力は正式Sourceまたは採用済み修正ではない。

指摘の採否判断、修正、再確認およびWRITE責任は、元の制作・修正責任側が保持する。

ただし、`AI_ORGANIZATION.md` または専門Sourceにより、外部AIが正式な制作・修正担当として割り当てられている場合は、その定義済み権限を正とする。

単に外部監査へ使用したことだけを理由として、制作・修正・承認またはWRITE権限が付与されたとはみなさない。

## 13. 環境間受け渡し

環境間の受け渡しは、AIが実行可能な作業指示へ構造化する。

受け渡しには、少なくとも次を含める。

- 実行先
- 目的
- 対象成果物
- 対象稿
- 現在状態
- 参照必須Source
- 実行内容
- 変更可能範囲
- 変更禁止事項
- 必要なQA・監査
- 人間判断が必要な停止条件
- 完了条件
- 完了後の次工程
- 未解決事項

成果物が特定人物のVoiceを担う場合は、必要に応じて次も受け渡す。

- 誰のVoiceを担う成果物か
- Voice OSの適用対象となる箇所
- 参照すべきVoice OS

Voice OSの具体的な適用判断は、本Sourceで新しく定義せず、`REPOSITORY_RULES.md`、`VOICE_OS.md` および適用される専門Sourceを正とする。

Chatの全履歴やWorkの全対話を、必要性を確認せず後工程へ渡さない。

正式Sourceから取得できる情報を、毎回受け渡し文へ全文複製しない。後工程がRepositoryを直接参照できる場合は、参照先と適用範囲を示す。

現時点で環境間を技術的に自動接続できない場合は、送信元AIが完成した実行指示を生成し、人間は原則として受け渡し操作だけを行う暫定運用を許容する。

人間に、環境ごとに目的、Source、制約または完了条件を再構成させない。

この貼り付け・運搬操作自体も、目標状態では削減対象とする。

## 14. 人間判断とChatエスカレーション

## 15. E2E自動進行

本事業では、成果物完成条件駆動のE2Eワークフローを標準形として目指す。

本節で示す自動起動・自動継続の実装状態は、§19「目標状態と将来拡張」を参照する。

本節は、現在すべての環境が自動接続済みであることや、すべての工程を無人実行できることを意味しない。

代表的なE2E工程には、必要に応じて次を含む。

企画・目的確定\
→ 制作\
→ 内部監査\
→ 権限内の修正\
→ 影響確認\
→ 再監査\
→ 必要な外部AI監査\
→ 指摘妥当性評価\
→ 必要な修正\
→ 再確認\
→ 必要な専門レビュー・正式承認\
→ 最終稿確定\
→ 必要なRepository統合\
→ CHANGELOG要否判定・必要な更新\
→ 構造・配置・参照・命名・差分・整合性確認\
→ 必要なcommit\
→ 必要なpush\
→ remote反映確認\
→ 完了

人間判断が不要な工程では、工程が移行したことだけを理由に停止しない。

「作って」「更新して」等の制作・変更GOは、目的、対象、影響範囲、適用Sourceおよび完了条件が確定している場合、その成果物に定義された完成条件まで進める起動指示として扱うことができる。

commit・pushまで自動進行できるのは、承認済みの作業目的・変更範囲・完了条件に当該工程が含まれる場合に限る。

具体的な自動進行、停止、再承認、実行環境・プラットフォームの権限確認、安全機構および個別指示との関係は、`HUMAN_IN_THE_LOOP.md` を正とする。

「commitしないで」「今回は監査後で止めて」「公開しないで」等の個別指示は、`HUMAN_IN_THE_LOOP.md` が定める範囲で当該作業に適用する。

本Sourceは、個別指示の優先順位、解除条件または恒久化ルールを独自に定義しない。

E2E自動進行は、完全無人化や人間承認の代行を意味しない。

人間判断が必要になった場合は、§14に従ってChatへ接続する。

## 16. 作業中状態と正式状態

環境上の所在・反映状態と、専門領域の承認Statusを混同しない。

環境横断では、少なくとも次の事実を区別する。

- Chatで検討中
- Chatで人間判断確定
- Workで制作中
- Workで監査提出可能
- ローカル作業ツリーへWRITE済み
- 構造・配置・参照・命名・差分・整合性の必要確認が完了
- commit済み
- GitHubへpush済み

これらは、教材等の `Draft`、`Review`、`Approved`、`Deprecated` と同じStatus体系ではない。

専門領域に既存Statusがある場合は、その正式基準を使用する。

「RepositoryへWRITE済み」「commit済み」「push済み」であることだけを理由として、成果物へApprovedを付与しない。

Work内で監査提出可能になったことも、人間承認または専門Source上の正式承認を意味しない。

各環境は、現在の所在・工程状態と正式承認状態を区別して受け渡す。

本Sourceは、環境横断の新しい正式Status体系を設けない。

## 17. モバイル運用

Chatは、モバイル環境から次を行う人間判断UIとして利用できる。

- 壁打ち
- 企画
- 方針決定
- 採否判断
- 人間承認
- AIワークフローの起動
- エスカレーションへの回答

目的は、人間の可処分時間を判断、創造および承認へ集中させることである。

移動中等にChatしか利用できない場合でも、人間判断を前倒しし、承認後の制作、監査、修正および実装工程を可能な範囲で進行させる。

人間がPC環境へ戻ること自体を、後続工程開始の必須条件にしない。

ただし、人間本人によるPC上の認証、権限操作、実ファイル確認その他の必須作業がある場合は、`HUMAN_IN_THE_LOOP.md` と適用される専門Sourceに従う。

## 18. 異常時・環境間競合

エラー時の自己復旧、停止条件、rollbackおよび人間判断への接続は、`HUMAN_IN_THE_LOOP.md` を正とする。

本Sourceは、それらを独自に再定義しない。

環境接続上は、異常または停止が発生した場合に、少なくとも次を識別する。

- 問題が発生した環境
- 現在の作業対象
- 対象成果物と対象稿
- 完了済み工程
- 未完了工程
- ローカル作業ツリーその他の既存差分
- Work稿とRepository差分の関係
- 人間または別AIとの編集競合
- 再開可能な環境と地点

安全に一意復旧できる場合は、`HUMAN_IN_THE_LOOP.md` に従って再開する。

Work稿とRepository差分の採否、編集競合または現在の作業対象を一意に確定できない場合は、推測で統合しない。

停止時も、既存差分や完了済み成果を破棄しない。

人間判断が必要な場合は、§14に従ってChatへ接続する。

## 19. 目標状態と将来拡張

本事業が目指すTarget Stateは、人間がChatで目的、方針および必要な判断を確定した後、AIが適切な実行環境を選択し、必要なSourceを参照しながら、制作、監査、修正、Repository反映および状態同期までを接続できる状態である。

次の接続・自動化は、単なる「いつか検討する可能性がある機能」ではなく、今回の環境統一が明確に目指す目標状態の構成要素とする。

- Chat、Work、Codex間の自動引き継ぎ
- AIによる実行先の自動選択
- 外部AIへの監査パッケージ自動生成
- 外部AI監査結果の自動回収
- 正式Sourceと作業状態の適切な同期
- 成果物完成条件に基づくE2Eワークフローの自動起動・継続
- タスク管理との状態同期
- モバイルからのワークフロー起動・進捗確認
- 個別E2Eワークフローとの接続

ただし、これらは現時点では未実装または接続方法が未確定である。

本Sourceに目標状態として記載されたことを理由として、現在利用可能、すでに自動接続済み、正式導入済みまたは包括的な実行権限が付与済みであると判断しない。

現時点では、利用可能な環境と権限の範囲で運用し、技術的に自動接続できない地点では、AIが完成した受け渡し指示を生成し、人間が必要最小限の中継操作を行う。

目標状態への移行では、次を個別に確認する。

- 使用する技術と接続方法
- 正式Sourceと状態情報の保持場所
- 認証および権限
- 外部共有範囲
- エラー時の復旧
- 人間判断へ戻す経路
- 専門Sourceが要求するQA・監査・承認
- 導入後に削減される人間操作

次の事項は、Target Stateそのものとは別に、必要性が確認された場合の将来拡張として扱う。

- branch・pull request運用
- GitHub上の追加的な自動確認
- 新しい外部サービスとの接続
- 未定義の個別媒体・業務フロー
- AI組織上の新しい役割または責任分離

新しい運用制度、権限、外部操作または責任配置を正式導入する場合は、人間判断を経て、責任を持つSourceへ反映する。

## 21. 完了判断

環境横断作業は、ファイル生成、Work上の完成稿作成またはRepositoryへの保存だけでは完了しない。

当該作業の完了条件は、`HUMAN_IN_THE_LOOP.md`、`REPOSITORY_RULES.md`、`AI_ORGANIZATION.md` および適用される専門Sourceを正とする。

環境接続上は、次を確認する。

- 適用される責任Source上の必須工程が完了している
- §15のE2E工程のうち、当該作業に必要な工程が完了している
- 人間判断または正式承認待ちを完了と誤認していない
- 未解決事項が適切な責任主体またはChatへ接続されている
- 必要なRepository・Git反映状態を確認できる
- 元の作業環境と後続環境の状態が矛盾していない

個別指示で停止点が指定されている場合は、その地点への到達を報告する。

停止点への到達と、正式な全工程完了を混同しない。
